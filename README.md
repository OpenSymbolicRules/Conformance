# OpenSymbolicRules — Conformance

Language-neutral conformance suites for engines that execute OSR v1 rule sets
(for example `OpenSymbolicRules.OSRv1` in OpenSymbolicRules.jl).

Each suite is generated by the Lean reference rewriter `OSR.normalize`
(`OpenSymbolicRules/Lean`, `OSR/Rewrite.lean`).  Lean proves that rewriter
sound (`OSR.normalize_sound`): with the rules of any profile, a defined
expression rewrites to a defined expression with the same value.  An engine
that reproduces the suite applies the same rules at the same positions, in the
same order, as the proved engine, on these inputs.

## Layout

```
schemas/cases.schema.json            JSON Schema of a suite
suites/<name>/<name>.cases.json      cases
suites/<name>/<name>.osr.json        the rule set the cases were generated from
scripts/check_digests.py             suite and rule set must share a source digest
```

## Case format

```json
{
  "id": "default/pattern.trigonometry.pythagorean",
  "profile": "default",
  "input":    { "kind": "OMA", "...": "OpenMath 2.0 JSON" },
  "expected": { "kind": "OMI", "integer": 1 },
  "trace": ["trigonometry.pythagorean"],
  "normal": true
}
```

The suite header (`semantics`) fixes what an engine must implement:

- **domain**: the verification domain used to select rules (`real`);
- **rules**: the rules of the profile, unconditional only, in profile
  (priority) order;
- **strategy**: outermost-leftmost.  At each step, try the root with each
  rule in order, then the arguments left to right.  One rewrite per step;
- **matching**: syntactic.  A pattern variable occurring twice matches equal
  subterms, integers compare by value, and `OMV` in the input are constants;
- **fuel**: the step budget.  `normal` is `true` when no rule applies to
  `expected`.

An engine passes a case when its result equals `expected`, the sequence of
applied rule ids equals `trace`, and it reports a normal form exactly when
`normal` is `true`.

## Suites

| Suite | Cases | Inputs |
|---|---|---|
| `trigonometry` | 84 | 4 profiles × (13 rule patterns + 8 nested, literal and non-linear inputs) |
| `algebra` | 56 | 2 profiles × (20 rule patterns + 8 nested, conditional, literal and non-linear inputs) |
| `calculus` | 65 | 29 rule patterns, the same with another bound variable, and 7 inputs testing independence and non-matching |
| `integration` | 16 | 6 rule patterns, the same with another bound variable, and 4 inputs testing independence, a derivative and a lambda; refuted rules leave their patterns unchanged |
| `logic` | 150 | 3 profiles × (39 rule patterns + 11 nested, non-linear and quantified inputs), domain `boolean` |

The literal cases include `sin(t)^3 + cos(t)^3` and `sin(3t)`, which must
*not* match `x^2` and `2x`, and a power `x^2` that must match by integer value.
They are regression tests for a bug found in OSRv1: `BigInt` integers were
compared by identity.

## Usage

```bash
just check                         # schema validation and digest consistency
just update ../Lean/generated      # refresh from a Lean export
```
